# LAN peer protocol proposal

LAN-1 implements direct TCP pairing, confirmed sessions, and manual text records in the Rust core. Image transfer, retry policy, and local bulk transfer below are proposals. The LAN handshake uses a separate Noise domain from the Phase 2B in-memory fixtures. The Linux IPC version stays independent. See [security design](security.md) for the trust model and cryptographic choices.

## Encoding and limits

Encode each message as a deterministic CBOR array using a bounded decoder such as `minicbor`. In the schemas below, `bN` is a byte string of exactly N bytes, `b` is a bounded byte string, `text` is UTF-8, `uint` is a nonnegative integer, and `null` is an explicit CBOR null. Require exact tags, field counts and types, shortest encodings, and no trailing bytes. Reject indefinite lengths, maps, tags, and unknown opcodes. Check lengths, total buffer budgets, and allowed protocol state before allocating or acting. Authenticate Noise records before decoding the inner array. Each version has one fixed Noise suite per mode. Reject unsupported versions and never retry under a weaker suite or with unpinned keys. [RFC 8949 §4.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2), [minicbor](https://docs.rs/minicbor/latest/minicbor/)

| Limit | Initial value |
| --- | --- |
| LAN record including its envelope | 36 KiB of encoded message bytes |
| Noise message carried inside an envelope | 1 KiB per handshake flight, 34 KiB per ciphertext record |
| Connect and handshake | Two seconds to dial within a 10-second handshake budget. Handshake payloads are empty. Each listener processes one initial handshake at a time, and the peer core caps pending handshakes. |
| Pending pairing | Five minutes from invitation creation, including approval. One authenticated attempt per invitation and one live invitation per endpoint. |
| Peer sessions | At most 32 active trust records per endpoint, two established channels per peer (one initiated by each side), and one in-progress candidate per peer and initiating side. |
| Text and image | 16 KiB UTF-8 text, 10 MiB encoded image, 32 KiB raw image chunks. Mark delivery uncertain after 10 seconds without an acknowledgment following `Text` or `ImageEnd`. |
| Image receive budget | Two inbound images per endpoint. Expire after 15 seconds without progress or 120 seconds total. |

## QR invitation and pairing

A is the inviter and Noise responder. B is the scanner and Noise initiator. The QR or imported text is `lyteboard-lan:v1:` followed by unpadded base64url of this deterministic CBOR array. Cap the whole string at 512 ASCII bytes. [RFC 4648 §5](https://www.rfc-editor.org/rfc/rfc4648.html#section-5)

`[1, address:b, port:uint, invite_id:b16, invite_psk:b32, inviter_noise_key:b32, expires_at:uint]`

- The address is four IPv4 or sixteen unscoped IPv6 octets. Together with the nonzero port it identifies a reachable listener on the selected LAN interface. The scanner connects directly using these values as untrusted hints.
- `invite_id` is a random lookup selector. `invite_psk` is a separate uniformly random 32-byte secret generated by the OS RNG for Noise PSK 0. `inviter_noise_key` pins A's X25519 public key.
- `expires_at` is Unix time in seconds. B uses it for display and early rejection and allows values from `now - 60s` through `now + 360s` for clock skew. A enforces both the wall deadline and a five-minute monotonic deadline that counts suspend time. Linux uses a monotonic clock that counts suspend time. The fallback clock elsewhere relies on the wall deadline for time spent suspended. Restart, cancellation, and expiry invalidate the in-memory invite.

B validates the invite and selects A's pinned Noise key before flight 1. B connects to A and runs `XKpsk0` with the prologue below. On A, validate flight 1 before atomically reserving the invite. Invalid attempts leave it available. Once reserved, the invitation never returns to available, even after timeout, rejection, or disconnect. Both sides release the secret when the pairing handshake finishes or the attempt terminates. Drop late, parallel, and invalid attempts without a reason that discloses invitation state.

After flight 3, exchange encrypted pairing `Hello` records and display the first eight bytes of the final Noise handshake hash as 16 uppercase hex characters in four groups of four, separated by hyphens. Both users compare the entire code and explicitly approve on their own device. A mismatch, refusal, expired invitation, unexpected record, or key-binding conflict closes the attempt. Labels are plain display text without control characters. A sends `PairCommit` after both approvals and staging its trust record. B stages its own record before sending `PairStored`. After authenticating `PairStored`, A saves local trust and emits `PairDone`, reporting that peer completion is still unconfirmed. B activates its record only after authenticating `PairDone`. Pairing transports carry only pairing records and close after completion or failure.

Pending records authorize no sessions. A disconnect before `PairDone` reaches B can leave A active and B inactive. This cannot establish a usable paired session. Discard provisional state on timeout, cancellation, drop, or restart. A confirmed KK session can resolve uncertainty if both sides did commit. Otherwise, explicitly remove the one-sided binding and use a fresh invitation. Reconnect never creates trust. Keeping B provisional until `PairDone` prevents it from activating after a lost `PairStored`.

## Peer channels

Use one ordered TCP stream per pairing or paired session and a four-byte big-endian length before each frame. Reject zero or oversized lengths before allocation. A partial frame and each write have a five-second deadline. An application receive call also waits at most five seconds for the first byte. Waiting for pairing approval uses the remaining invitation window.

A frame body uses `[1, 4, from:b32, to:b32, channel:b16, kind:uint, invite_id_or_null, body:b]`. Kinds 0–3 represent pairing open, session open, later handshake flights, and transport ciphertext. The invite selector is present only on pairing open. `from` and `to` carry Noise static public keys in cleartext and must match the channel. The frame body carries a Noise message.

The Noise prologue is `["lyteboard.lan.tcp", 1, mode:uint, channel:b16, initiator:b32, responder:b32, invite_id_or_null]`. Mode 0 is pairing and mode 1 is an established-peer handshake. The claimed initiator and responder keys are ordered by role, and the initiator generates a fresh channel ID. The remote static from Noise must match the claimed key before trust changes or application delivery. Addresses are used only to dial.

Use active local pins to start KK. Both Noise flights carry empty payloads. After `Split`, the initiator sends encrypted `Ready` first. The responder verifies it before returning encrypted `Ready`. The initiator verifies the reply before sending user data. Ordered reliable paths are required. Close the channel on an invalid tag, unexpected phase, truncated frame, out-of-order record, or known failed send. A skipped ciphertext cannot be recovered by continuing the same transport. A candidate replaces an older session from the same initiator only after fresh key confirmation. Outstanding transfers on the old channel fail and may be retried at the application level.

### Encrypted peer records

`id` is a random `b16` transfer ID. All fields below, including tags, are inside Noise transport encryption. Bind local user approval to one specific pairing transcript.

| State and tag | Array | Meaning |
| --- | --- | --- |
| Pairing | `[lan_version, 0, label:text]` | `Hello`, label at most 64 UTF-8 bytes. Both devices send it after the handshake. |
| Pairing | `[lan_version, 1]`, `[lan_version, 2]`, `[lan_version, 3]`, `[lan_version, 4]` | `PairApprove` (B), `PairCommit` (A), `PairStored` (B), `PairDone` (A), in order. |
| Pairing | `[lan_version, 5]` | `PairReject`. Close the attempt. |
| Session | `[lan_version, 6]` | `Ready`, in the key confirmation order above. |
| Session | `[lan_version, 7, id, text]` | `Text`. Require nonempty UTF-8 without NUL within the text limit. |
| Session | `[lan_version, 8, id, media:uint, total:uint, sha256:b32]` | `ImageBegin`. Media `1` PNG, `2` JPEG, `3` WebP. `total` is the nonzero encoded byte count within the image limit. |
| Session | `[lan_version, 9, id]` | `ImageReady`. Receiver reserved an image slot. |
| Session | `[lan_version, 10, id, index:uint, chunk:b]` | `ImageChunk`. Start at index zero, contiguous, every chunk exactly 32 KiB except the final remainder. |
| Session | `[lan_version, 11, id]` | `ImageEnd`. Verify complete size, digest, and allowed format before acceptance. |
| Session | `[lan_version, 12, id, result:uint]` | `DeliveryAck`. `0` accepted, `1` previously accepted. This means the receiving endpoint accepted the transfer and gives no guarantee of a paste or durable history. |
| Session | `[lan_version, 13, id_or_null, code:uint]` | `PeerError`. `1` invalid payload, `2` too large, `3` unsupported media, `4` integrity failed, `5` busy, `6` timed out, `7` denied. |
| Session | `[lan_version, 14]` | Authenticated `Close`. Incomplete transfers are discarded. |

Send chunks only after `ImageReady`. The receiver accepts no extra chunks after the declared total. Compare the incremental SHA-256 digest with the authenticated manifest. Identify the actual format and use bounded decoding before rendering. Initial decode targets are one concurrent decoder per endpoint, at most 16 million pixels, 8,192 pixels on either axis, 64 MiB decoded output, and no animated images. Keep incomplete data in bounded memory and discard it on timeout, disconnect, cancel, revocation, or validation failure. An interrupted image starts from byte zero on retry.

For one recipient use one session and one transfer ID. For multiple recipients, including broadcast to the active trust list, send independently encrypted copies with per-recipient IDs, limits, and delivery results. No group key. Retain each recipient's ID for retry and never reuse an ID for new content. The receiver serializes acceptance by `(pinned sender Noise key, transfer ID)` across channels. Keep completed IDs in a memory-only cache for up to 24 hours, capped at 256 per peer and 4,096 total. A known completed ID returns a duplicate acknowledgment without publication or an image slot. A second in-progress transfer with the same ID gets `busy`. Deduplication is best-effort across cache eviction or restart. Do not promise exactly-once delivery.

On transport loss, LAN-1 discards session keys. The caller can redial the QR address and establish a fresh channel with new Noise state. The Linux profile saves the QR endpoint on the scanner and refreshes the dial hint after a successful outbound session. The current protocol carries no scanner listener address. An address change can interrupt automatic reconnection until discovery or manual IP fallback is available. Surface authentication failures without changing pins. Retry connections with exponential backoff and jitter starting at 1 second and capped at 60 seconds. A failed attempt does not imply that previous user data was delivered. Retry a transfer only while it is still explicitly pending in the local sender, with the same ID and fresh encryption.

## Future local bulk transfer

Keep the verified 4 KiB IPC framing unchanged. Future control requests can authorize a bounded import or export using a random one-shot `b16` handle tied to the local UID, direction, expected length, and operation. A second user-private stream socket such as `$XDG_RUNTIME_DIR/lyteboard/transfer.sock` checks kernel peer credentials and consumes the handle in a bounded preamble. Expire unused handles after 30 seconds. Stream only the declared number of bytes, enforce the same payload ceilings, per-user slot budgets and deadlines, and abort on partial streams. No arbitrary paths, client-supplied identity, or base64 image buffers in the control IPC. Windows can provide the equivalent named-pipe adapter. Android can use bounded in-process buffers through UniFFI.
