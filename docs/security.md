# Security design

Phase 2B implements pairing and encrypted peer sessions in the Rust core. LAN-1 adds direct TCP with in-memory trust. OS credential adapters and clipboard integration are planned. [Architecture](architecture.md), [Wire protocol](protocol.md)

## Threat model

| Threat | Control and residual risk |
| --- | --- |
| Interception, impersonation, or modification | The QR pins the inviter's key and conveys a high-entropy secret. Users compare the completed transcript and approve on both devices. Reconnects use both pinned keys. Noise authenticates encrypted records. LAN observers can see addresses, public Noise key selectors, traffic lengths, and timing. |
| Unauthorized devices or invitation theft | The inviter permits one authenticated attempt within five minutes. Possession of the QR can reserve that attempt and cause denial of service. The intended participants must actually compare codes over a trusted channel and both approve. A replaced QR, skipped comparison, or deceived user can establish the wrong trust. |
| Replay and truncation | Use fresh Noise handshakes and ordered transport counters, explicit image completion, and authenticated acknowledgments. A replayed handshake initiation may consume work and cannot establish a usable session by itself. Bounded application deduplication covers ordinary retries. |
| Compromised or revoked device | Any currently trusted device can read what it receives and can send valid content as itself. Local revocation cuts off future acceptance and tears down sessions. It cannot recall information already disclosed, revoke trust on another endpoint, or protect an actively compromised OS or app. |
| Local keys, clipboard data, or history exposure | Secrets use OS credential storage. History defaults off. Bound memory use and minimize secret residency. An unlocked credential store, same-user processes on desktop, administrator access, swap, crash dumps, and other apps reading the local clipboard can defeat local confidentiality. |
| LAN resource exhaustion | Bound pre-authentication connections, frame lengths, read and write deadlines, and queues. Local attackers can still disrupt connectivity. |

Trust the receiving endpoint and its OS, the local frontend and daemon acting for the user, the credential store, the OS RNG, and the pairing comparison channel. Protected peer data includes text, image bytes and digests, labels exchanged in pairing, and application acknowledgments. Noise cannot hide the fact that devices communicate or hide content from an intended recipient. The LAN exposes connection metadata to network observers. No telemetry or clipboard payload logging. Redact invitations, comparison codes, key material, and raw protocol messages from diagnostics. [Noise application responsibilities](https://noiseprotocol.org/noise.html), [Linux IPC boundary](daemon.md#protocol-and-trust-boundary)

## Selected cryptography

Use Noise revision 34 via Snow 0.10.0 as the evaluated baseline. The suite is X25519, ChaCha20-Poly1305, and SHA-256. Snow implements the handshake, transcript, key derivation, authenticated encryption, and ordered transport counters. The `noise-protocol` crate also implements Noise and leaves more transport state management to the caller. Verify Snow's patch level and advisories at implementation time. The project states that Snow has had no formal audit. External review of the application protocol and dependency review are release gates. [Noise specification §§5–9, 12–14](https://noiseprotocol.org/noise.html), [Snow documentation](https://docs.rs/snow/0.10.0/snow/), [Snow upstream](https://github.com/mcginty/snow), [Resolved Snow nonce advisory](https://github.com/mcginty/snow/security/advisories/GHSA-7g9j-g5jg-3vv3), [noise-protocol](https://docs.rs/crate/noise-protocol/latest)

| Property | Mechanism |
| --- | --- |
| Pairing | `Noise_XKpsk0_25519_ChaChaPoly_SHA256` uses fundamental XK with the standard `psk0` modifier. The inviter's static key is known before flight 1. The invite secret occupies PSK slot 0. The inviter learns the scanner's authenticated static key in flight 3. An `XXpsk0` variant would require explicitly checking the inviter's key against the QR pin after flight 2. XK makes the expected inviter key part of the handshake. |
| Paired authentication and reconnection | `Noise_KK_25519_ChaChaPoly_SHA256` uses both previously pinned statics. Start a fresh handshake with empty payloads for every reconnection. Confirm the new transport in both directions before application traffic. |
| Record integrity and confidentiality | Snow's stateful `TransportState` authenticates each record with ChaCha20-Poly1305 and separate directional keys from Noise `Split`. Application code never chooses nonces, rolls counters back, or retries ciphertext. |
| Forward secrecy | Fresh ephemeral–ephemeral DH contributes to the confirmed traffic keys. Empty handshake payloads avoid exposing data under the weaker guarantees of early flights. Later theft of the static keys alone does not reveal previously recorded, confirmed traffic when old ephemeral and session secrets are unavailable. This is not post-compromise recovery or a guarantee about earlier stored content or captured live process memory. |
| Replay resistance and key lifecycle | A fresh handshake and context identify each channel. Keep exactly one ordered reader and writer per transport. Close on authentication, ordering, or framing failure. End the session at one hour or 2^20 encrypted records in either direction, whichever comes first. Re-handshake with new ephemeral keys. Do not resume keys, export raw keys, or use 0-RTT. |
| Image integrity and random values | Use RustCrypto `sha2` SHA-256 for the complete image digest carried in an authenticated manifest. Use the OS CSPRNG through `getrandom` or the library's OS-backed RNG for keys, invitation secrets, challenges, and IDs. Abort on RNG failure. |

For every X25519 operation, require a contributory result. Snow 0.10.0's default resolver does not reject the all-zero shared secret. Use its resolver interface with an X25519 provider backed by `x25519-dalek` and `was_contributory()`. Reject before emitting any handshake response or persisting a peer key when DH fails. Phase 2B must demonstrate this for static and ephemeral inputs and run known-answer and interoperability tests. The adapter delegates all cryptographic operations to library primitives. Keep invitation secrets and app-owned key buffers in zeroizing storage where possible. Dropping Snow state limits reuse but does not establish verified memory erasure. [Snow X25519 source](https://github.com/mcginty/snow/blob/v0.10.0/src/resolvers/default.rs), [Snow resolver API](https://docs.rs/snow/0.10.0/snow/resolvers/trait.CryptoResolver.html), [X25519 contributory check](https://docs.rs/x25519-dalek/latest/x25519_dalek/struct.SharedSecret.html#method.was_contributory), [Snow zeroization issue](https://github.com/mcginty/snow/issues/203), [Ed25519 strict verification](https://docs.rs/ed25519-dalek/latest/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict)

The QR secret is 32 uniformly random bytes. A human-chosen PIN lacks the entropy Noise requires for a PSK. The 64-bit comparison code checks a completed transcript in addition to the pinned key and random secret. It serves no role as a password or key and carries no standalone short-code authentication guarantee. Compare the code shown on the two trusted device displays, in person or over an independently authenticated channel. [Noise PSK rules and transcript binding](https://noiseprotocol.org/noise.html)

## Device trust and local storage

- The LAN protocol uses the authenticated X25519 public key as the device identity. LAN-1 keeps the pin, display label, and trust state in memory, with the caller holding the connection hint. The Phase 2B regression fixtures retain their separate Ed25519 route binding. Only active local pins authorize sessions.
- A fresh, explicitly confirmed invitation creates trust. Pending and revoked records authorize no sessions. Local revocation records durable tombstones, invalidates matching sessions and pending transfers, and prevents future use of the recorded key binding. An operation that publishes clipboard content must still have an active trust record at commit time. The user may explicitly authorize a fresh pairing with a previously revoked identity. Never refresh the key binding based on an address change or an unsolicited claim.
- Session key rotation is automatic through full handshakes. Reset or compromise of a persistent identity requires generating a new persistent identity, removing the old identity on other devices, and pairing again with each peer. There is no account recovery, global revocation list, or private-key export in v1.
- The Linux design stores seeds using Secret Service, Windows uses user-scoped DPAPI, and Android uses an Android Keystore-backed wrapping key and app-private ciphertext. Fail closed if the credential store is locked or unavailable. Do not silently generate a replacement identity or write plaintext seeds as a fallback. Select and test the concrete credential adapters before enabling durable identities. Keep cryptographic state inside the Rust core. A future UniFFI interface exposes bounded, typed operations and public identifiers, with platform key storage supplied through an internal adapter. [Secret Service](https://specifications.freedesktop.org/secret-service/latest/), [Windows DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata), [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [UniFFI](https://mozilla.github.io/uniffi-rs/latest/)
- Keep the trust database private to the local OS user. Store no clipboard contents on disk by default. Enable optional durable history only after choosing and testing authenticated at-rest encryption, key separation, backup exclusion, retention, and deletion. Do not promise secure file erasure or protection from software running in the user's unlocked session.

## Decisions before release
